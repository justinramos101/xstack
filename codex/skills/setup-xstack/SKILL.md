# Set up xstack

Read [Host runtime](../poteto-mode/references/host-runtime.md). Write the active host's model roles where that host loads them into every session: `~/.claude/rules/xstack-models.md` on Claude Code, or a marked block in Codex's global instructions file, `${CODEX_HOME:-~/.codex}/AGENTS.md`, or `AGENTS.override.md` in that folder when it has content, because Codex then loads it instead. On Hermes Agent, write `${HERMES_HOME:-~/.hermes}/xstack-models.md`, which workflows read through the script. `scripts/models.mjs` in this skill's directory reads and writes all three, so never edit them by hand here.

1. Detect. Identify Claude Code, Codex, or Hermes Agent. The detected models are the values the subagent spawn tool accepts in this session. On Claude Code, they are the `model` values the `Agent` tool schema lists, and the efforts are its `effort` values. On Codex, they are the models `spawn_agent`'s description lists, each with the reasoning efforts listed beside it. On Hermes, roles name delegation routes, not models: the detected values are the names in the `option` enum on `delegate_task`'s tasks, each with its description, which the `advanced-delegation` plugin adds when `delegation.backend` is `model_map`. Each route already fixes its provider, model, and reasoning effort, so a Hermes entry never takes an `@ effort`. If the tool has no `option` field, the only value is `inherit-parent`, and every child runs on `delegation.model`, else the parent's model. Then offer the setup once: `hermes plugins install advanced-delegation --enable`, then `hermes delegation config` to create at least a fast coding route and a stronger judgment route, such as `fast` and `deep`, plus a route on another vendor for panel diversity. Let the user run it, because it writes their Hermes config, and the routes reach a new session only. A `profile` field instead (`profile_routes`) runs a child as a whole Hermes profile with its own persona and skills; do not map roles to it. If the tool lists nothing, ask the user for the models they know they can use. Do not assume a model is available because a document names it. `inherit-parent` and `auto` are always valid.
2. Read. Run `node <this skill directory>/scripts/models.mjs read <claude|codex|hermes>`. It prints the current roles and names their file on stderr: the host's loaded file, or the legacy shared `~/.agents/xstack-models.md` when this host has not been written yet. With no file, it prints xstack's defaults for the host. A role a file leaves out also takes its default, which `models.mjs <claude|codex|hermes> "<role>"` prints. A line whose role is not in the script's `roles` export, such as `how critics`, is from a retired role, and the write drops it. A model from another host, such as a `gpt-*` model in a Claude Code config or a Claude model in a Codex config, becomes `inherit-parent`. On Hermes, an entry that is not a detected route name becomes `inherit-parent`. Drop comment lines that recorded caveats this run resolves, such as unverified effort routing on a host whose spawn tool now takes an effort.
3. Budget. On Hermes, skip this step and say why: effort is set on each route, so the budget stays `unlimited`, and `hermes delegation config` changes a route's `reasoning_effort`. Elsewhere, ask for a budget unless the user already gave one, and name the current one. With no config, say that `large` matches the defaults. Offer `unlimited` to keep each entry's effort, `large` for xhigh, `medium` for high, or `small` for medium. A budget other than `unlimited` caps each entry's effort at its level and gives that level to an entry with no effort. It never raises an explicit lower effort, and no workflow raises effort past the cap. Budgets are reasoning targets, not spending limits. When a model does not support the target, offer its highest effort at or below the target and show what will actually run.
4. Map. On Hermes, map to route names by their descriptions, the same way. Prefer a fast coding model for feature, refactoring, bug-fix, perf-issue, hillclimb, explorers, investigators, and swarm workers. Prefer a stronger reasoning model for judgment, explanation, synthesis, and the hardest tasks. Start every role from its current value, or its default when unset. The defaults follow pstack's split: its Grok roles run on the parent on Claude Code and on `gpt-6.1-sol` on Codex, and its Opus roles run on `opus` and `gpt-6-astra`, all at xhigh. A default model the spawn tool does not list needs a choice. Default panels have four entries, the judgment model and the coding model twice over, so a review gets four independent reads from two models. Arena runners, architect runners, and interrogate reviewers run one subagent per entry. The arena cross-judge pool lists alternatives, and arena picks one judge from it. Offer distinct models when the host has them, and say when it has only one.
5. Confirm. Show every role with its model and effort, mark any model not in the detected set as needing a choice, and list each line step 2 dropped or changed. Ask only about choices the user's request leaves open. Write each entry as `model @ effort` only when the spawn tool accepts both.
6. Write. Pipe the confirmed lines, the `# budget` line first (no budget line on Hermes), to `node <this skill directory>/scripts/models.mjs write <claude|codex|hermes>`. It validates every line, overwrites the Claude Code rule or the Hermes roles file, or replaces only the xstack block in the Codex instructions file it chose and keeps the rest of that file as it was. It never edits the file Codex is not loading. It prints the file it wrote. Never put the role lines anywhere else, and keep secrets out of them. Leave the legacy file in place, because the other host may still read it, and tell the user they can delete it once both hosts are written.
7. Check. Resolve every role with `node <this skill directory>/scripts/models.mjs <claude|codex|hermes> "<role>"` and compare each model and effort with the detected set. The script checks syntax and precedence, not account entitlement. If delegation is available, spawn one subagent with a configured role's model and effort and confirm it ran from the host's record, not the subagent's own answer: on Claude Code, the subagent's `model` and `effort` in its transcript metadata; on Codex, the child's `turn_context` model and effort in its session rollout; on Hermes, the `route` in the child's `delegate_task` result, which names the option and the provider, model, and effort it actually ran on. Otherwise say runtime routing is unverified.
8. Report. Name the file written and say the roles load in new sessions; the current session still has the old ones.
9. Offer a verification skill. If the project has no way to drive its real app, neither a `verify-*` skill nor an existing harness, offer once to generate one with create-verification-skill, so agents can drive the app the way a user does and prove changes work. On yes, run it. On no, move on.
10. Offer a formal verification skill. If the project has no formal verification skill, meaning a project skill that runs a model checker, a proof, or another verifier against the code, offer once to generate one with create-formal-verification-skill, so agents can prove a key property holds in every case in scope, not only the cases tests reach. On yes, run it. On no, move on.

Example draft for step 6, with the Codex defaults:

```text
# budget: large
feature, refactoring, bug-fix, perf-issue, hillclimb: gpt-6.1-sol @ xhigh
how explorer, why investigators, reflect tooling, swarm workers: gpt-6.1-sol @ xhigh
judgment and prose, hardest tasks: gpt-6-astra @ xhigh
how explainer, why synthesizer: gpt-6-astra @ xhigh
reflect judgment, divergent, synthesizer: gpt-6-astra @ xhigh
arena runners: gpt-6-astra @ xhigh, gpt-6.1-sol @ xhigh, gpt-6-astra @ xhigh, gpt-6.1-sol @ xhigh
arena cross-judge pool: gpt-6-astra @ xhigh, gpt-6.1-sol @ xhigh, gpt-6-astra @ xhigh, gpt-6.1-sol @ xhigh
architect runners: gpt-6-astra @ xhigh, gpt-6.1-sol @ xhigh, gpt-6-astra @ xhigh, gpt-6.1-sol @ xhigh
interrogate reviewers: gpt-6-astra @ xhigh, gpt-6.1-sol @ xhigh, gpt-6-astra @ xhigh, gpt-6.1-sol @ xhigh
```

The Claude Code defaults put `opus @ xhigh` in place of `gpt-6-astra @ xhigh` and `inherit-parent` in place of `gpt-6.1-sol @ xhigh`. The Hermes defaults put `inherit-parent` in place of both, since xstack cannot know a user's route names. A Hermes draft with `fast` and `deep` routes reads like `feature: fast`, `hardest tasks: deep`, and `interrogate reviewers: deep, fast, alt, fast`, with no `@ effort` and no budget line.

On Claude Code, a configured line reads like `feature: opus @ xhigh`. On Codex, it reads like `feature: gpt-6.1-sol @ high`. Repeated inherited entries keep reviews independent but add no model diversity. Host restrictions on overriding a loaded agent take precedence over the configured roles.
